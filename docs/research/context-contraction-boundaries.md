# Context-contraction boundaries across agent implementations

## Scope and method

This note answers [research ticket #12](https://github.com/taylorrowser/pi-observational-memory/issues/12) from primary sources only. “Top-level task” means one user submission whose agent may make several model/tool steps before settling. “Atomic cut boundary” means the earliest point at which an implementation may replace exact history without creating an invalid or semantically partial tool interaction.

Pinned sources:

- Mastra at [`cadd3a276f8e0026e3c84cffe935538419cb890c`](https://github.com/mastra-ai/mastra/tree/cadd3a276f8e0026e3c84cffe935538419cb890c).
- Pi v0.81.1 at [`20be4b18d4c57487f8993d2762bace129f0cf7c6`](https://github.com/earendil-works/pi/tree/20be4b18d4c57487f8993d2762bace129f0cf7c6), plus the downstream `pi-v0.81.1-patch.3` release metadata and complete local docs previously identified by this repository’s Pi lifecycle research.[^pi-release]

- Aider at [`5dc9490bb35f9729ef2c95d00a19ccd30c26339c`](https://github.com/Aider-AI/aider/tree/5dc9490bb35f9729ef2c95d00a19ccd30c26339c).

## Executive answer

**Verified:** Mastra, OpenHands, Cline, and OpenCode can all contract context *between model/tool steps of one top-level task*. Pi v0.81.1 cannot do ordinary threshold compaction between provider calls inside its low-level agent/tool run: it checks only after that run ends (plus before the next top-level prompt). Pi can still compact and retry inside the outer busy period after an overflow terminates a low-level run.[^pi-run-loop] Mastra prepares observational memory before every agentic step and explicitly performs threshold observation at steps greater than zero; OpenHands runs its condenser before every agent step; Cline’s compaction callback is defined to run before every model request; and OpenCode checks completed-step usage inside its session loop, then inserts and processes a compaction task before continuing.[^mastra-step][^openhands-loop][^cline-trigger][^opencode-loop]

**Verified:** None of the well-tested implementations treats “last _N_ arbitrary messages” as a sufficient boundary. Pi forbids cuts at tool results; Cline likewise permits a retained tail to start at a typed user message or assistant message, never a tool-result-only user message; OpenHands computes the intersection of manipulation boundaries for tool pairs, parallel batches, and (for signed-thinking models) whole tool loops; Mastra refuses to observe while the latest step still contains a tool invocation in `state: 'call'`; OpenCode stores call and result state in one assistant tool part and converts even interrupted pending parts to paired error outputs.[^pi-cut][^cline-cut][^openhands-atomicity][^mastra-incomplete-tools][^opencode-tool-parts]

**Verified:** The retained tail is implementation-specific:

- **Mastra:** by default, activation aims to leave 20% of the 30k raw-message threshold, i.e. about **6k exact raw tokens**, at buffered-chunk boundaries. Selection guards against leaving fewer than `min(1000, retentionFloor)` tokens where a viable boundary exists; synchronous cleanup backs off rather than remove below the retention floor. It is a target/floor algorithm, not a fixed number of turns.[^mastra-defaults][^mastra-retention]
- **Pi:** approximately **20k recent tokens** by default, beginning at the nearest valid user-like or assistant entry. A single oversized turn may be split: its exact suffix remains, while its user request and early work move into a dedicated turn-prefix summary.[^pi-doc-compaction][^pi-prepare]
- **OpenHands:** preserves the first `keep_first` events (application default **2**) and an exact suffix. Event-count contraction targets a total post-condensation view of half `max_size` (application default `max_size=240`, hence a nominal 117 suffix events after two fixed head events and one summary); token contraction chooses a suffix that reduces the view to half `max_tokens`. Both ends snap outward to valid manipulation indices, so the actual suffix can be shorter. A hard reset exceptionally replaces the whole view with one summary.[^openhands-defaults][^openhands-forgetting]
- **Cline (agentic strategy):** **20k recent tokens** by default, snapped to a safe user/assistant boundary, while never summarizing away the latest typed user prompt. A single long first task may therefore retain only a safe assistant-starting suffix plus summary; a later latest user turn is retained whole even if that exceeds the nominal tail budget.[^cline-tail]
- **OpenCode:** at most the most recent **two user turns**, additionally constrained by a raw-tail budget equal to 25% of usable context clamped to **2k–8k tokens**. It keeps whole recent turns newest-first where they fit, then may keep a message-level suffix of one oversized turn; if no suffix fits, it keeps no raw tail and summarizes the full history.[^opencode-tail]

**Interpretation:** The strongest common design is not “summarize old messages.” It is **canonical raw log + boundary-safe exact tail + explicit compressed state + deterministic recovery behavior**. Mastra adds a second compressed layer (reflection) and explicit `current-task` / `suggested-response` sidecars. OpenHands, Pi, Cline, and OpenCode instead iteratively fold an earlier summary into the next summary; Cline also persists a validated compaction projection sidecar, while OpenCode separately prunes old tool outputs before full summarization.[^mastra-layers][^cline-sidecar][^opencode-prune]

## Verified behavior by implementation

### Mastra observational memory

Mastra’s processor models one user-facing turn as multiple agentic steps. At step 0 it may activate already-buffered observations and reflect them. On every step it checks token status and may start fire-and-forget observation buffering; at step > 0 it first persists the prior step and can synchronously observe/clean up before the next model generation.[^mastra-step] A dedicated mid-loop suite asserts that observation on step `N > 0` removes observed messages and reduces the next step’s context.[^mastra-mid-loop-test] This is a direct affirmative answer to the key timing question: contraction is designed to happen during a long tool-using turn, not only between user messages.

The safety gate is explicit. Before either buffering or synchronous observation, the processor inspects the latest step parts. If any tool invocation is still in `state: 'call'`, both paths are skipped. Tests exercise async and sync cases, verify no Observer call while the invocation is pending, mutate it to a result, and then verify observation proceeds on a later step.[^mastra-incomplete-tools-test]

Normal activation retires raw history by exact message IDs recorded in buffered chunks; marker-aware cleanup can also retain only unobserved parts of a partially observed message. Pending input/response message IDs are passed as protected IDs during fallback filtering.[^mastra-filter] The default activation policy buffers every 20% of a 30k message threshold and activates enough chunks to retain 20%, nominally 6k tokens. Boundary selection prefers the closest over-target chunk but falls back to an under-target boundary if overshoot is too large or would leave too little raw context; synchronous cleanup independently restores removals until the configured retention floor is met.[^mastra-retention]

Mastra’s tail is therefore **exact but not fixed to turns**, and its “6k” is a policy target/floor rather than an unconditional equality. In an exceptional chunk layout with no safe under-boundary, activation can choose the closest over-boundary; source explicitly calls this “better than nothing.”[^mastra-retention]

The compressed past is layered. The actor sees active observations plus the unobserved raw tail; a Reflector creates a new generation when observations themselves cross their threshold. Observer output also extracts `current-task` and `suggested-response`, which are stored outside the observation prose and reinjected later. Retrieval mode can retain source ranges and expose exact recall.[^mastra-layers] Besides threshold activation, the pinned implementation can activate prepared buffers after idle time or provider/model change to align contraction with cache boundaries.[^mastra-early-activation]

Evidence is strongest for mechanism, not outcome magnitude. The repo contains a multi-step long-session test that simulates turns with up to five tool steps and asserts persistence/activation/reflection behavior, plus the pending-tool tests above and a LongMemEval harness/config matrix. The pinned snapshot does not contain result tables proving the docs’ broad compression/quality claims.[^mastra-long-test][^mastra-longmemeval]

### Pi v0.81.1

Pi’s outer `_runAgentPrompt()` awaits a complete low-level `agent.prompt()`, then invokes `_handlePostAgentRun()`; post-run logic prioritizes retry, then calls `_checkCompaction()`, then checks queues. A separate check immediately before a new prompt catches an aborted previous response.[^pi-run-loop] The local release docs depict the same lifecycle: a “turn” repeats model/tool activity, `agent_end` precedes possible retry/compaction, and `agent_settled` means no retry, compaction, or continuation remains.[^pi-release-lifecycle]

Thus Pi does **not** proactively compact before each provider request in a healthy low-level tool loop. Threshold compaction happens after that run and does not itself resume work. Overflow is different: Pi removes the failed assistant from in-memory context, compacts, and returns `true` so the enclosing outer loop calls `agent.continue()`; this can preserve one top-level user submission while replacing its low-level run.[^pi-overflow]

The cut algorithm walks backward until estimated retained content reaches `keepRecentTokens`, then chooses the nearest valid entry at or after that point. Valid boundaries are context-visible user-like or assistant messages. Tool results are explicitly forbidden because they must follow their tool call; starting at an assistant tool-call message keeps all following results.[^pi-cut] The default release setting is 20k recent tokens.[^pi-settings]

If the boundary is a user-like message, the exact tail begins there. If one tool-heavy turn itself exceeds the budget, Pi may cut at an assistant message. It then summarizes complete older turns separately from the discarded prefix of the split turn, whose prompt requires `Original Request`, `Early Progress`, and `Context for Suffix`; only the assistant-starting suffix remains exact.[^pi-prepare] Repeated compaction supplies the previous structured summary while re-summarizing messages that used to be in the retained window, so there is one rolling compressed layer rather than a separate observation/reflection hierarchy.[^pi-repeat]

The tests cover token-based cut selection, split-turn detection, repeated compaction, a large real session fixture, reconstruction after compaction, queue continuation after auto-compaction, and one-shot overflow recovery. They are structural and lifecycle tests; no benchmark establishes that the 20k choice is quality-optimal.[^pi-tests]

A downstream-doc caveat matters: `pi-v0.81.1-patch.3/docs/session-format.md` also describes a newer materialized `retainedTail` checkpoint shape. The pinned upstream commit used for this comparison stores `firstKeptEntryId` and reconstructs summary + pre-compaction kept entries + post-compaction entries. This note treats the upstream commit as authoritative for v0.81.1 core behavior and cites downstream docs only where they agree on lifecycle/defaults.[^pi-session-context]

### OpenHands 1.36

OpenHands keeps an append-only event log and derives an LLM `View`. Before every agent step, `prepare_llm_messages()` invokes the condenser. If it returns a `Condensation`, the agent appends that event and returns without sampling another action; the conversation’s outer `while` loop takes another step. Provider context-window and malformed-history errors append a `CondensationRequest`, also causing the next step to contract before retrying.[^openhands-loop]

The normal condenser keeps `keep_first` exact head events and a boundary-adjusted exact suffix. For event-count pressure it computes a target of `max_size // 2`; for token pressure it computes the suffix needed to reduce to `max_tokens // 2`; explicit requests target half the current view. If several reasons apply, it chooses the smallest suffix (the most aggressive contraction). It then snaps both forgetting boundaries forward to valid manipulation indices.[^openhands-forgetting]

Those indices are the key safety mechanism:

1. **Tool-call matching:** there is no boundary between an action and its corresponding observation while any call is pending.[^openhands-tool-match]
2. **Parallel batch atomicity:** action events from one LLM response share an `llm_response_id` and cannot be split.[^openhands-batch]
3. **Tool-loop atomicity:** for loops beginning with signed thinking, all consecutive action/observation batches remain one unit so provider checksums and thinking placement stay valid.[^openhands-tool-loop]

Tests pin concrete legal index sets for single, multi-batch, and parallel tool loops. The default-value test says `max_size=240` was raised to make room for long tool loops; the OpenHands application’s constructor relies on SDK defaults `max_size=240`, `keep_first=2` unless a user overrides size.[^openhands-boundary-tests][^openhands-defaults]

OpenHands treats event-count pressure as **soft**: if no valid atomic range exists, it sends the uncondensed view and tries next step. Configured token pressure and explicit/provider-recovery requests are **hard**: inability to make normal progress causes a hard reset that summarizes the whole view, retries with progressively truncated event strings, and retains no exact head/tail.[^openhands-hard-soft]

Its only summary layer is recursive: a `Condensation` is an append-only tombstone containing forgotten event IDs and an inserted summary event; later condensation can summarize that prior summary again. The official README says this strategy “performs well in benchmarks,” but this source snapshot provides no result table. It does provide unit boundary tests and optional, non-blocking real-model condenser tests for thinking signatures, hard reset, delayed soft contraction, token triggers, and event-count triggers on Claude Opus 4.5 and GPT-5.1 Codex Max.[^openhands-readme][^openhands-integration-tests]

### Cline SDK compaction

Cline’s context pipeline defines compaction as a `prepareTurn` callback “before each model request.” When enabled, it estimates the complete provider-safe request (system prompt, tools, and messages) and proactively compacts at 90% of effective input capacity. The default built-in strategy is agentic summarization; manual compaction is also supported.[^cline-trigger]

The agentic path walks backward toward a default 20k tail. A tail may start at a typed user message or an assistant message, but never at a tool-result-only user message. If a later typed user turn exists, the cut is moved to or before that prompt so the whole latest turn survives. For a single top-level task whose user message is index 0, a very long tool loop can still be split at an assistant boundary.[^cline-tail]

The result is one synthetic user summary plus the exact suffix. On repeated passes, only material after the latest compaction-summary message is folded into the previous summary. A persisted sidecar records the compacted projection, source message count, and source-prefix hash; if the canonical prefix still matches on a later turn, the sidecar’s compacted messages are combined with newly appended canonical messages. Re-compaction starts from that projection rather than rebuilding from full raw history.[^cline-agentic][^cline-sidecar]

If the agentic model call fails (other than cancellation), Cline falls back to its basic non-LLM compactor. That fallback has a different continuity surface: typed prompts are mandatory selection anchors (although the final hard-ceiling projection may truncate an individually oversized prompt); the latest turn keeps the newest suffix that fits and snaps forward to an assistant boundary; older turns may keep their concluding assistant text; dropped tool activity is attached to user prompts as deterministic notices; and output of prior basic compactions is marked frozen. It removes or retains tool pairs atomically.[^cline-basic]

The unit suite directly asserts no orphaned tool pairs for old, latest, and parallel multi-tool batches; exact preservation of the latest typed prompt; safe snapping when a budget lands inside a pair; repeated compaction without duplicate folds; agentic summary + recent tail; and fallback behavior. No first-party benchmark result in the pinned source establishes that 90%/20k is optimal.[^cline-tests]

### OpenCode

OpenCode’s session loop examines the last finished assistant step before creating the next model request. If its reported total usage reaches “usable” context—input limit less a configurable reserve, or context less maximum output—it appends a synthetic compaction task and continues the same loop. Provider context-overflow errors also make the processor return `compact`, which appends the same task with overflow metadata.[^opencode-loop][^opencode-overflow]

Tail selection first identifies normal user turns. By default it considers only the latest two. Its token budget defaults to 25% of usable context, clamped to 2k–8k. Whole turns are retained newest-first if they fit; on the first oversized candidate turn, `splitTurn()` searches forward from the user message for the earliest message suffix that fits. If no suffix fits and no newer turn was retained, there is no exact tail and the entire history goes to the summary.[^opencode-tail]

OpenCode can use message boundaries safely because each assistant `ToolPart` stores call input and terminal output/error together. Conversion emits an `output-available` pair for completed calls and a synthetic error output for pending/running calls, preventing dangling tool-use blocks. The compaction summary receives only the selected head (with media stripped and tool output capped at 2,000 characters); successful compaction records `tail_start_id`, and context reconstruction orders compaction marker + summary + exact tail + later continuation.[^opencode-tool-parts][^opencode-filter]

Normal auto-compaction adds a synthetic “continue if you have next steps” user message. Repeated compaction passes the prior summary in a dedicated anchored block. Separately, a proactive prune pass may clear old completed tool outputs: it protects the latest 40k tool-output tokens and only commits pruning when more than 20k tokens can be removed; `skill` output is exempt.[^opencode-repeat][^opencode-prune]

Tests cover reserve-aware overflow detection, compaction marker creation, pruning, retained `tail_start_id`, token-budget shrinking, split-turn suffix retention, full-summary fallback, synthetic continuation, provider overflow replay, and repeated summaries/tails. They establish protocol behavior, not end-task quality; no benchmark result is checked into the cited source.[^opencode-tests]

## Cross-implementation findings

### 1. “Can contract during one task” is a first-class architectural choice

**Verified:** Mastra, OpenHands, Cline, and OpenCode put contraction on a seam reached between low-level model/tool steps. Pi puts conventional compaction after its low-level agent run. Therefore Pi’s existing extension `context` hook can rewrite each request, but Pi’s conventional compactor cannot guarantee headroom during a single unusually long tool loop.[^pi-run-loop][^pi-release-lifecycle]

**Interpretation:** A Pi observational-memory implementation that promises long-turn continuity must own a **per-request or per-step policy**, not only `turn_end`/`agent_settled`. Observation may be produced asynchronously, but retirement of exact raw context must be committed synchronously before the request that needs the space.

### 2. Provider-valid atomicity is necessary but not always sufficient

**Verified:** Pi and Cline protect call/result pairs. OpenHands additionally protects parallel response batches and whole signed-thinking tool loops. Mastra blocks observation until the active tool invocation has a result. OpenCode avoids split protocol records by co-locating call/result state.[^pi-cut][^cline-cut][^openhands-atomicity][^mastra-incomplete-tools][^opencode-tool-parts]

**Interpretation:** Pi’s observational-memory cut unit should be a **completed agent step/batch**, not merely “not a `toolResult`.” The continuity contract should require:

- every retained tool result has its retained call;
- every retained call has one terminal result/error;
- parallel calls from one assistant response move together unless the provider representation proves independent;
- an in-flight call is never observed-and-retired;
- signed reasoning/tool-loop blocks move according to provider constraints;
- semantic outcomes of retired tool work survive even when the raw protocol is valid without them.

### 3. A token count alone does not specify the exact tail

**Verified:** All token-based systems snap to coarser boundaries. Pi’s 20k and Cline’s 20k are approximate after snapping. Mastra uses chunk boundaries plus a floor. OpenHands can retain substantially more or less because manipulation indices encompass a whole loop. OpenCode combines a turn-count cap with a small token cap and may retain no raw tail.[^pi-cut][^mastra-retention][^openhands-forgetting][^cline-tail][^opencode-tail]

**Interpretation:** Pi’s contract should state the algorithm, not just “keep 20k”: e.g. **retain the newest completed atomic units until a target, protect the active task anchor, and define what happens when one atomic unit exceeds the budget**. It must also state whether the tail is a target, minimum, maximum, or best effort.

### 4. Long single-turn coding tasks expose the decisive failure mode

**Verified:** Pi can split an oversized turn at an assistant entry and summarize the original request; Cline explicitly allows an assistant-starting suffix for a single long first task; OpenHands may be unable to condense at all when one tool loop spans almost the entire view; Mastra waits only for the currently incomplete call, then may observe completed earlier steps in that same turn; OpenCode can retain a suffix of an oversized turn.[^pi-prepare][^cline-tail][^openhands-hard-soft][^mastra-step][^opencode-tail]

**Interpretation:** “Keep the latest user turn verbatim” is neither always feasible nor sufficient. Pi observational memory should preserve an explicit **active-task anchor** outside prose observations: original user intent, current plan/state, unresolved decisions, latest verified tool outcomes, pending next action, and blockers. Mastra’s `current-task` / `suggested-response` sidecar is the clearest precedent.

### 5. Repeated contraction needs an anchored update model

**Verified:** Pi, OpenHands, Cline, and OpenCode all feed a previous summary into later contraction, directly or because the prior summary is itself in the event view. Mastra instead appends observations and only later reflects them into a new generation. Cline validates persisted compacted state against the canonical transcript prefix.[^pi-repeat][^openhands-readme][^cline-sidecar][^opencode-repeat][^mastra-layers]

**Interpretation:** For Pi, an append-only observation journal plus versioned reflection/synthesis is safer than repeatedly rewriting one opaque summary. The journal/reflection state should remain a branch-scoped sidecar while the raw JSONL remains canonical. Any projected context should carry a source boundary/hash so it cannot be replayed onto a divergent branch.

### 6. Failure policy is part of continuity

**Verified:** OpenHands distinguishes soft deferral from hard full reset. Cline falls back from agentic to deterministic basic compaction. OpenCode can fall back to summary-only when no tail fits and stops if summary generation itself overflows. Pi leaves a failed threshold compaction unperformed and bounds overflow recovery to one attempt. Mastra’s async buffering failure is non-fatal, whereas synchronous observation failure is surfaced.[^openhands-hard-soft][^cline-basic][^opencode-tail][^pi-overflow][^mastra-failure]

**Interpretation:** Pi’s contract should prohibit silent continuity degradation. If observation is late or invalid, keep raw context while headroom permits; at hard pressure, use a visible, deterministic degraded mode; and record whether the resulting memory is normal, partial, or emergency-reset state.

## Implications for Pi’s observational-memory continuity contract

The following are **design implications**, not claims about current Pi behavior:

1. **Two timing guarantees:** distinguish background observation from synchronous retirement. Background work may run after completed steps; retirement must happen on the per-request `context` seam before unsafe headroom is consumed.
2. **A semantic atomic unit:** define it as a completed assistant step including its parallel call batch, all terminal results/errors, and provider-coupled reasoning—not simply a session entry.
3. **A precise tail rule:** specify target/floor/cap, boundary snapping, and oversized-unit behavior. Preserve the top-level task verbatim when feasible; otherwise promote it into a typed active-task sidecar before cutting.
4. **Explicit continuity state:** at minimum retain original goal, constraints, current work, completed outcomes, unresolved questions, changed/read files, next action, and error/blocker state. Do not rely on a prose observation log to rediscover these.
5. **Canonical transcript and provenance:** never destructively delete raw session history. Persist memory branch-scoped with source entry IDs or a prefix hash, generation, observer model/prompt version, and a status indicating complete/partial/emergency observation.
6. **Layered compression:** let exact raw steps become append-only observations; only rewrite observations through a separately versioned reflection/synthesis boundary. Keep exact recall available for source wording and large tool outputs.
7. **Visible hard-pressure behavior:** late observation should defer contraction; hard overflow should choose a documented emergency path rather than silently presenting stale memory as complete.
8. **Cache-aware stability:** activate prepared memory in coarse, stable chunks rather than rewriting the prompt every request. This is an optimization subordinate to the atomicity and continuity guarantees.

## Required evidence before claiming continuity

Existing projects mostly prove protocol safety, not task quality. A Pi implementation should at least add:

- **Boundary/property tests:** random transcripts with sequential and parallel tools; assert no orphan calls/results, no duplicate result, no cut inside in-flight or provider-coupled batches.
- **Long-single-task tests:** one user task with many tool steps, including a single oversized result, cancellation, tool error, steering message, model switch, and contraction more than once.
- **State/provenance tests:** branch/fork/tree navigation, resume, divergent-prefix rejection, repeated reflection generations, exact recall, and stale/partial observer output.
- **Provider replay tests:** submit post-contraction contexts to Anthropic-, OpenAI-, and Gemini-shaped validators or live canaries, including signed thinking and parallel calls.
- **Quality benchmarks:** compare full history, Pi conventional compaction, and observational memory on task completion, regression rate, continuation correctness, factual recall, unnecessary repeated tool calls, latency, cache hit rate, and total accounted cost. Report raw result tables and confidence intervals; a harness or structural unit suite is not outcome evidence.

## Bottom line

**Verified:** Implementations that contract inside a tool loop do so at a pre-request/pre-step seam and pair that timing with stronger boundaries than arbitrary message truncation. The most conservative boundary is OpenHands’ completed manipulation unit; the richest continuity state is Mastra’s observations + reflection + explicit task/response hints + raw tail. Pi v0.81.1 has a sound call/result cut rule and split-turn summary, but its conventional compaction timing is post-run and therefore cannot by itself protect a single healthy tool loop before its next provider call.

**Interpretation:** Pi observational memory should combine those strengths: **per-request headroom control, completed-step atomicity, an exact recent tail with an explicit oversized-step rule, branch-provenanced append-only observations, separate active-task state, layered reflection, and visible emergency degradation**. That is a defensible continuity contract; “keep about 20k tokens and summarize the rest” is not.
